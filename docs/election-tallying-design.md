# 工代会选举计票系统设计文档

状态：产品规则、页面方案 A、票号复用规则与基础技术栈已确认，等待发布形态决策和正式实现
日期：2026-08-26
适用活动：上海燃气有限公司工会委员会第二届“两委”委员选举（2026-08-31）

## 1. 目标

为现场计票员提供一个局域网网页工具，用更少的操作录入纸质选票，并实时汇总两项互相独立的委员选举结果。

系统是计票效率工具，不代替现场人员对纸质选票的人工判断，不自动宣布当选人，也没有“开始计票”或“结束计票”状态。

## 2. 第一版范围

第一版提供：

- 四个录入身份：工会第一组、工会第二组、工会第三组、经审组。
- 两项独立选举的选票录入、人工无效、超额无效、撤销与重录。
- 所有连接设备实时查看总票数、有效票、无效票和候选人排名。
- 管理员分别清空任一选举或同时清空两项选举。
- 管理员分别配置两项选举的投票人数上限。
- 服务器数据库持久化已提交和已撤销记录。
- 当前浏览器保存尚未提交的草稿。
- 录入页显示当前录入组与当前选举的录入进度。

第一版不提供：

- 个人账号或严格的身份认证。
- 自动判断印章、笔迹或符号是否合格。
- 当选人自动判定。
- 录入页操作进度之外的分组统计、无效原因分类或人工无效原因。
- Excel、CSV、PDF 或打印导出。
- 清空后的备份与恢复。
- 候选人或应选人数配置页面。

## 4. 系统拓扑

```text
服务器电脑
├── Web 服务
├── SQLite 数据库
└── 局域网访问地址
      ├── 工会第一组笔记本
      ├── 工会第二组笔记本
      ├── 工会第三组笔记本
      └── 经审组笔记本
```

任意笔记本都可选择一个录入身份。身份选择不是安全边界，只用于记录归属和限制撤销范围。所有设备均可查看实时总结果。

## 5. 选票录入规则

### 5.1 初始状态

- 每张新选票的所有正式候选人默认选择“赞成”。
- 每名正式候选人始终且只能处于“赞成、反对、弃权”之一。
- 提交成功后立即建立下一张草稿，重新恢复全员赞成。

默认全员赞成会使两项选举的新草稿都处于赞成超额状态。这是刻意设计：它对应快速录入纸票时只修改反对和弃权项的工作方式，并不阻止录入真实的超额无效票。

### 5.2 另选人

- 每名另选人计 1 张赞成票，反对票固定为 0。
- `另选人数 <= 正式候选人反对数`。
- 弃权不产生另选名额。
- 姓名提交前去除首尾空格，其他文字严格匹配。
- 同一张票内不得重复同一另选人。
- 另选人不得与本选举的正式候选人同名。
- 不满足规则时禁止提交，并明确指出需要修正的姓名或数量。

### 5.3 有效性

定义：

```text
用于有效票判定的赞成总数 = 正式候选人赞成数
```

满足以下全部条件时为有效票：

- 未被计票员人工标记为无效。
- 工会委员会选举赞成总数不超过 23；经费审查委员会选举赞成总数不超过 7。
- 另选人规则全部满足。

无效票分为两种输入路径，但结果只汇总为一个无效票数：

- 超额无效：赞成总数超过应选人数。点击“提交本票”后提示将作为无效票计入，确认后允许提交。
- 人工无效：点击“记为无效票”，确认后直接提交，不填写原因。

任何无效票都不计入正式候选人或另选人的个人票数。

## 6. 记录生命周期

### 6.1 提交

- 每项选举拥有一个由所有录入组共享的票号池，范围为 `1..投票人数上限`。
- 每条记录拥有永久且不可复用的内部记录编号；票号只表示未撤销记录当前占用的可复用号码。
- 提交在服务器事务中完成，服务端原子检查当前未撤销记录数小于该选举配置的投票人数上限，并分配当前最小的可用票号。
- 三个工会录入组并发提交时，未撤销记录的票号必须唯一且总数不得超过该选举配置的投票人数上限。
- 提交结果包含票号、选举、录入组、选择明细、另选人、有效状态和提交时间。
- 当未撤销记录数达到投票人数上限时，未撤销记录的票号集合必须严格等于从 1 到投票人数上限的完整范围。

### 6.2 撤销与重录

- 各录入组可以查看并撤销本组的任意记录。
- 历史列表显示票号、提交时间和有效/无效/已撤销状态；点击记录查看完整票面。
- 未撤销记录显示当前票号；已撤销记录的票号显示为 `-`。撤销前票号仅作为审计数据保存在数据库中，不在界面任何位置显示。
- 历史默认按提交时间倒序展示，并保留切换为提交时间正序的能力；提交时间相同时使用永久记录编号保证顺序稳定。永久记录编号不在界面显示。
- 撤销不修改原记录，也不删除历史，而是将记录状态改为“已撤销”。
- 已撤销记录不参与投票人数上限和任何统计。
- 撤销后，该记录不再拥有当前票号，其原票号立即返回本选举的共享票号池。
- 后续任何录入组提交的新记录都取得当时最小的可用票号。新记录是独立记录，不与任何已撤销记录建立替代关系。

### 6.3 清空

- 管理员可清空工会委员会选举、清空经费审查委员会选举，或同时清空两项选举。
- 管理员页面使用简单口令，不建立个人管理员账号。
- 管理员可分别修改两项选举的投票人数上限；新上限不得低于当前未撤销记录的最大票号。
- 清空必须二次确认。
- 清空永久删除目标选举的全部记录并使票号池重新从 1 开始，不产生备份。
- 清空后，所有客户端收到新的数据版本并丢弃对应选举的旧草稿，避免旧草稿重新写入新一轮计数。

## 7. 实时统计

每项选举分别计算并展示：

- 已录入总数：所有未撤销记录数。
- 有效票：所有未撤销且有效的记录数。
- 无效票：所有未撤销且无效的记录数，不区分超额无效与人工无效。
- 每名正式候选人和另选人的赞成票、反对票、弃权票与名次。

页面显示正式候选人的弃权票数；弃权数不参与排名。另选人的反对票和弃权票恒为 0。

### 7.1 排名规则

所有正式候选人和另选人进入同一排名：

1. 赞成票降序。
2. 赞成票相同时，反对票升序。
3. 两项均相同时，共享竞赛排名，例如 `1、2、2、4`。
4. 共享名次的候选人按姓名拼音序展示，展示顺序不改变名次。

排名只是计票结果，不代表系统自动宣布当选。

## 8. 页面设计

### 8.1 入口与全局导航

- 首次进入显示正式的录入组选择页，不预设任何组别。
- 入口将四个组别按选举归属分区展示：工会第一组、工会第二组、工会第三组只能录入工会委员会选票；经审组只能录入经费审查委员会选票。
- 选择组别后，系统唯一确定该设备可录入的选举类型；组别和选举类型不作为两个可自由组合的筛选项。
- 当前浏览器会话保持所选组别，顶部持续显示当前组和固定选举，并提供明确的“切换组别”操作。
- 入口同时提供“直接查看实时结果”，查看结果不要求先选择录入组。
- 主导航包含“选票录入、录入历史、实时结果”。
- 页面始终显示服务器连接状态和当前录入身份。
- 笔记本电脑是主要设备，布局优先保证 1366 x 768 及以上视口中的录入效率。

### 8.2 选票录入

- 录入页不提供选举类型切换。三个工会组固定录入工会委员会选票，经审组固定录入经费审查委员会选票。
- 录入页显示“本组已录入”和“本选举已录入 / 上限”。两个已录入数都只统计未撤销记录，无论记录有效或无效；该信息仅作为录入操作进度，不进入实时结果页或正式分组统计。
- 工会选举的三个录入组共享本选举总数和投票人数上限；经审选举只有一个录入组，仍同时显示本组数与本选举总数以保持界面一致。
- 桌面端的录入进度固定在右侧栏顶部、本票汇总之前；窄屏将录入进度放在候选人列表之前。
- 候选人姓名与“赞成、反对、弃权”应在同一视觉单元中，状态清晰且点击区域足够大。
- 页面固定显示赞成、反对、弃权和另选人数，以及当前票将判为有效还是无效。
- 另选人区域显示可用名额 `反对数 - 已填写另选人数`。
- 有效票直接提交；超额无效和人工无效均需确认。
- 提交成功反馈包含服务器分配的票号。
- 达到投票人数上限时，录入进度高亮并禁用有效票与无效票提交入口；服务端仍执行最终上限校验。
- 并发提交导致服务端拒绝时保留当前草稿并立即刷新进度。撤销释放容量后自动重新启用提交入口，但绝不自动提交草稿，录入员必须手动再次点击。
- 首次无法获取录入进度时显示占位信息且不单独阻止提交；后续刷新失败时保留上次数据并提示更新失败。上次快照已经满额时继续禁用提交，直到获取到未满的新快照。

### 8.3 录入历史

- 默认只展示当前录入组的记录。
- 选举类型由当前组固定，不提供跨选举历史切换。
- 每条记录显示票号、时间、有效/无效/已撤销状态；已撤销记录的票号显示为 `-`。
- 撤销前票号和永久记录编号均不在界面显示。
- 默认按提交时间倒序展示，并可切换为提交时间正序。
- 展开后以只读方式还原完整选择和另选人。
- 未撤销记录提供“撤销”操作并需要确认。

### 8.4 实时结果

- 通过“工会委员会、经费审查委员会”两个页签切换。
- 顶部显示已录入、有效票、无效票。
- 排名表显示名次、候选人、类型（正式/另选）、赞成票、反对票、弃权票。
- 所有设备都能查看，服务器数据变化后自动刷新。

### 8.5 管理页面

- 输入管理员口令后可分别配置两项选举的投票人数上限，也可执行三个危险操作：分别清空两项选举、同时清空。
- 不提供开始、结束、锁定、导出、恢复或其他选举配置。
- 清空确认框必须明确显示目标与永久删除后果。

### 8.6 已确认的页面方案

正式实现采用原型 A“密集表格式”，不再继续评估 B“票面网格式”和 C“异常优先式”。

方案 A 的固定结构：

- 首屏是正式的录入组选择入口，组别唯一决定可录入的选举类型。
- 进入后使用紧凑的顶部品牌栏和主导航，持续显示服务器状态、当前录入组及其固定选举。
- 录入工作台采用左右布局：左侧为双列候选人表，右侧为固定的本票汇总、有效性提示、另选人和提交操作。
- 每名候选人在同一行中展示姓名及“赞成、反对、弃权”分段选择，默认赞成，反对或弃权后整行产生明显但克制的状态变化。
- 右侧汇总始终显示赞成、反对、弃权数量和当前有效性，避免计票员滚动候选人列表后失去总体判断。
- 实时结果与录入历史延续表格式信息密度，不采用卡片排行榜或强调装饰性的仪表盘。
- 笔记本视口优先；窄屏保证可用，但不作为正式计票的主要操作环境。

## 9. 数据与一致性设计

### 9.1 服务器数据

建议使用以下概念数据：

- `election_state`：选举标识、数据版本、投票人数上限。
- `ballot_record`：永久记录编号、票号分配值、选举、录入组、状态、有效性、提交与撤销时间。撤销后保留原票号分配值作为不展示的审计数据，但只有未撤销记录拥有当前票号。
- `listed_choice`：选票、正式候选人、赞成/反对/弃权。
- `write_in_choice`：选票、标准化后的姓名、原始显示姓名。

正式候选人配置保存在代码中；投票人数上限保存在数据库中并通过管理页面配置。

同一选举内，票号唯一约束只适用于未撤销记录。永久记录编号在全部历史记录中始终唯一。

### 9.2 浏览器数据

- 当前录入身份。
- 两项选举各自尚未提交的选票草稿。
- 草稿所属的服务器数据版本。

浏览器草稿不进入实时统计。提交成功、切换身份、管理员清空导致版本变化时，应按规则清理或提示处理草稿。

### 9.3 实时同步

- 服务端是所有已提交记录和统计结果的唯一权威来源。
- 录入进度使用专用只读查询，在同一个服务端快照中返回本组未撤销记录数、本选举未撤销记录总数、投票人数上限和数据版本；不得为了计数读取完整录入历史。
- 客户端每 2 秒轮询数据版本；提交、撤销、清空或修改投票人数上限导致版本变化后，重新读取权威数据。
- 当前设备提交成功或被服务端以投票人数上限拒绝后，立即重新读取录入进度，不等待下一轮轮询。
- 断线时禁止假装提交成功；恢复连接后重新获取服务器状态，并保留尚未提交且版本仍匹配的草稿。

## 10. 验收场景

1. 三个工会录入组同时提交，服务器从共享票号池分配不重复的最小可用票号，未撤销总数不超过当前配置的投票人数上限。
2. 经审组默认 8 人全部赞成，系统提示赞成超额；确认后记录为无效票且不增加个人票数。
3. 工会票将 3 人改为反对后成为 23 人赞成的有效票。
4. 一张票有 2 人反对时最多填写 2 名另选人；第 3 名被禁止提交。
5. 弃权人数增加不会增加另选名额。
6. 同一票重复另选人或填写正式候选人姓名时禁止提交。
7. 人工无效票不要求原因，提交后只增加总票数和无效票数。
8. 撤销第 20 号记录后，它退出统计，历史票号显示为 `-`，20 号回到共享票号池；如果 20 是最小空缺，任何组下一次提交的新记录都取得 20 号，且两条记录之间没有替代关系。
9. 达到当前配置的投票人数上限后拒绝新提交；撤销一张后允许提交。
10. 两名候选人赞成、反对均相同时名次相同，并按拼音序展示。
11. 清空单项选举不影响另一项；同时清空将两项都归零。
12. 浏览器刷新可恢复未提交草稿；服务器重启可恢复全部已提交和已撤销记录。
13. 管理员修改任一选举的投票人数上限后立即生效并在服务器重启后保留；低于当前未撤销记录最大票号的配置被拒绝，系统不自动重编号。
14. 本组提交有效票或无效票后，本组已录入数与本选举已录入总数都立即加一；其他组提交时只有本选举总数增加。
15. 撤销记录后对应的本组数和本选举总数都减一；清空选举后两个数归零且投票人数上限保持不变。
16. 本选举已录入总数等于投票人数上限时，页面高亮满额状态并禁用两种提交入口。
17. 两个录入组并发争夺最后一个名额时，失败方保留草稿；撤销释放容量后按钮自动恢复，但不会自动提交。
18. 窄屏设备无需滚过候选人列表即可看到录入进度；进度刷新失败不绕过服务端的投票人数上限校验。
19. 同时存在多个空缺票号时，后续提交依次取得当前最小空缺号；重新满额后，未撤销记录的票号集合严格等于 `1..投票人数上限`。
20. 历史默认按提交时间倒序展示并可切换为正序；时间相同的记录仍保持确定顺序。

## 11. 原型验证问题

页面原型只回答以下问题，不作为生产代码：

- 26 名候选人的高密度录入采用表格、票面网格还是“只关注非赞成项”的布局更高效？
- 赞成超额状态怎样持续可见，又不妨碍真实无效票录入？
- 实时结果和当前录入状态应占据多大视觉权重？
- 在 1366 x 768 笔记本视口中，是否能不迷失当前位置地完成整张票录入？

原型使用内存模拟数据，不连接 SQLite，也不代表正式实现的组件或代码结构。

原型结论：采用 A“密集表格式”。其双列候选人表、右侧固定汇总栏和正式组别入口进入正式设计；B、C 作为已完成的比较材料保留在一次性 HTML 原型中，不进入生产实现。

## 12. 技术方案

### 12.1 已确认的基础技术栈

- 前端：React、TypeScript、Vite。
- 服务端：Hono、TypeScript，运行在 Node.js 长期支持版本上。
- 数据库：SQLite、Drizzle ORM、better-sqlite3；数据库文件只存放在服务器电脑本地磁盘。
- 包管理：pnpm。
- 部署单元：一台服务器电脑运行一个应用服务，同时提供前端静态文件、业务接口和实时结果更新；录入电脑只需使用浏览器访问局域网地址。

### 12.2 实现边界

- React 只负责浏览器界面、草稿和交互状态；所有已提交记录、票号、票数上限和统计结果以服务端为准。
- Hono 提供 HTTP 接口；客户端每 2 秒轮询数据版本，发现变化后重新读取权威统计结果与录入进度。
- SQLite 的提交、撤销、清空、最小可用票号分配、投票人数上限修改和上限检查必须放在数据库事务中完成。
- 数据库结构由 Drizzle schema 定义，使用 Drizzle Kit 生成并保存版本化 SQL 迁移；服务启动时只执行已纳入版本控制的迁移，不在现场使用 `push` 修改结构。
- 第一版不引入独立前端状态库、组件库、第二套数据访问层、消息队列、容器编排或外部数据库服务。
- 候选人和选举规则作为版本化的代码配置保存；选票记录及其选择明细保存在 SQLite 中。

### 12.3 票号规则切换

- 部署包含可复用票号规则的新版本前，管理员必须在旧版本管理页面执行“两项选举全部清空”。
- 该操作删除两项选举的有效和已撤销记录，使新版本从空票号池开始工作，并保留两项选举已配置的投票人数上限。
- 本次设计不迁移既有票记录，也不规定遗漏部署前清空时的自动处理行为。

### 12.4 待确认的工程决策

- Node.js、Drizzle ORM 与 better-sqlite3 的固定版本组合。
- 服务器电脑是预装 Node.js，还是交付包含 Node.js 运行时的 Windows 免安装目录。
- 管理员口令的首次配置与本地保存方式。
